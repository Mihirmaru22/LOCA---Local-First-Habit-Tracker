# Phase R · R4 — AI for Personal Intelligence (In Depth)

> **Mission:** learn what *actually works* when software tries to model a person over time — memory, knowledge graphs, temporal/causal reasoning, uncertainty, provenance, and human‑AI collaboration — so LOCA's "intelligence" is built on honest epistemics instead of confident guesses.
>
> **Format:** every book and topic ends with the standard five blocks — **Lessons for LOCA · Anti‑patterns · Design implications · Open research questions · Ideas to experiment with** — tied to D1–D4.
>
> **The thesis R4 argues:** *personal intelligence is an epistemics problem, not a modeling problem.* The systems that work are honest about what they know, where it came from, and how sure they are — and they get corrected by the human. LOCA already computes the right primitives (`UncertaintyCalculus`, `InferenceProvenance`, `FeedbackProcessor`, `SensorConflict`) and then **throws them away at the UI (F8)** while shipping **uncalibrated inference (F1)**. LOCA's AI problem is not "too simple a model" — it's **broken epistemics on top of a model that overreaches its data.** R4 also warns against the opposite failure: reaching for LLMs / agents / vector DBs to paper over an epistemics gap that more machinery only hides.

> **Honesty note on LOCA today:** LOCA's current "AI" is a *deterministic, hand‑weighted inference engine* (energy/stress/focus/mood) + a *correlation detector* (`PatternDetectionEngine`) + a *people knowledge‑graph extractor* + *temporal event/chapter detection*. It uses **no LLM, no embeddings, no vector store, no RAG.** So R4 sorts every topic into **(a) fixes to the epistemics of what exists now** (immediate, D3/D4) vs **(b) architectural options for a possible V3+** (forward‑looking, adopt only if they serve the user, not to look sophisticated).

## Part A — What a personal‑intelligence system actually needs

Across the literature, the systems that successfully model a person share five properties — and LOCA's status on each:

1. **Grounding over generation.** Claims are tied to retrieved evidence, not fabricated. → LOCA fabricates a baseline (F6) and hides its grounding (F8).
2. **Calibrated uncertainty.** The system's confidence matches its accuracy; it widens when data is thin. → LOCA's `UncertaintyCalculus` exists but the UI ignores it; inference is miscalibrated (F1).
3. **Provenance/attribution.** Every derived fact points to its source. → LOCA computes `InferenceProvenance` then discards it (F8); seeded entities are unlabeled (F7).
4. **Human‑in‑the‑loop correction.** The user teaches the system; corrections update it. → LOCA has `FeedbackProcessor`/`SensorConflict` but surfaces no correction loop.
5. **Temporal/episodic memory.** A durable, timestamped, retrievable record of the person's life. → LOCA's strongest asset (the honest record); underused as a *memory/retrieval* system.

**The pattern:** LOCA has built the primitives of a good personal‑intelligence system and then inverted every one of them at the surface. The R4 work is not "add AI" — it's "**stop discarding the epistemics you already compute.**"

## Part B — Book notes

### 1. *Designing Machine Learning Systems* — Chip Huyen
Production ML is a **data + systems + monitoring** problem, not a modeling contest: data quality, feature engineering, **distribution shift**, and continuous **monitoring/feedback loops** dominate outcomes. Most failures are data and iteration failures, not algorithm failures.
- **Lessons for LOCA:** LOCA's failures are exactly this — a data/epistemics problem (thin signal, no baseline, no monitoring of whether inferences are right), not a model‑capacity problem. It needs **monitoring** (is the inference calibrated?) and a **feedback loop**, not a fancier model.
- **Anti‑patterns:** treating inference as fire‑and‑forget; no monitoring of prediction quality; ignoring distribution shift (a user with no sensors is a totally different data regime — F1).
- **Design implications:** instrument inference quality; treat sensor‑poor users as a distinct regime with its own (honest) behavior; build the correction feedback loop as core infrastructure.
- **Open research questions:** how does LOCA *know* its inferences are wrong without ground truth? Can micro‑check‑ins serve as a monitoring signal?
- **Ideas to experiment with:** an internal calibration dashboard comparing inferred states vs explicit check‑ins.

### 2. *AI Engineering* — Chip Huyen
Building on foundation models: **evaluation is the hard part**; prompt engineering, RAG, finetuning, and agents are tools chosen by need; guardrails and cost/latency matter. Don't reach for the heaviest tool first; evaluate rigorously.
- **Lessons for LOCA:** *if* LOCA ever adds an LLM (e.g. for reflective prompts or Ask), **evaluation and guardrails come first**, and RAG/grounding is preferred over free generation. But most of LOCA's problems need **no** LLM — beware adding one to look modern.
- **Anti‑patterns:** adopting LLMs/agents to seem sophisticated while the epistemics stay broken; shipping generative features without evaluation/guardrails.
- **Design implications:** if generation enters, ground it in the real record (RAG‑style) and evaluate for faithfulness; keep the deterministic record authoritative.
- **Open research questions:** where (if anywhere) does an LLM add honest value in LOCA — reflective prompts? Ask? — without introducing hallucination risk?
- **Ideas to experiment with:** a tightly‑grounded LLM that only *rephrases the real record into a reflective question*, never asserts new facts.

### 3. *Building LLM Applications for Production* — Chip Huyen
LLM apps need **control flow, retrieval grounding, guardrails, evaluation, and observability**; free‑form generation without grounding hallucinates; the durable value is in the scaffolding around the model, not the model.
- **Lessons for LOCA:** the lesson generalizes beyond LLMs — **the scaffolding (grounding, guardrails, evaluation) is the product.** LOCA's missing scaffolding is provenance + calibration + correction, regardless of whether a model is generative.
- **Anti‑patterns:** ungrounded generation; no guardrails on what the system may claim; no observability into claim quality.
- **Design implications:** guardrails that forbid any claim without evidence (the "evidence or silence" rule from Learning.md); observability on claims.
- **Open research questions:** what's the minimal guardrail set that guarantees LOCA never overclaims?
- **Ideas to experiment with:** a claim‑guardrail layer every Life statement must pass (has evidence? has confidence? within data support?).

### 4. *Designing Data‑Intensive Applications* — Martin Kleppmann
Reliability/scalability/maintainability; **immutable event logs** and **derived data** (the log is the source of truth, everything else is a materialized view you can rebuild); consistency; batch/stream processing. Provenance falls out naturally when the raw event log is immutable and derived views are recomputable.
- **Lessons for LOCA:** LOCA already has this shape — `SignalEvent`/`LogEntry` are the **immutable event log**; `InferredState`/patterns/chapters are **derived views** (and are recomputed idempotently — verified). This is architecturally *right*. The fix is to **carry provenance from log to view** so every derived claim can name the events it came from.
- **Anti‑patterns:** mutating or conflating the raw record with derived interpretation (Schacter's suggestibility risk, R2); derived views that can't point back to their source events.
- **Design implications:** keep the event log immutable and authoritative; make every derived view carry a pointer to its source events; provenance becomes a lineage query, not an afterthought.
- **Open research questions:** can LOCA expose "show me the events behind this claim" as a first‑class lineage feature?
- **Ideas to experiment with:** a tap‑through from any inferred state/pattern to the exact `SignalEvent`s that produced it.

### 5. *The Alignment Problem* — Brian Christian
ML systems optimize the objective you *gave* them, not the one you *meant*; reward misspecification, misgeneralization, and hidden bias are pervasive; **interpretability** and **human feedback** are central to closing the gap between objective and intent.
- **Lessons for LOCA:** LOCA's "objective" is implicitly "emit a state number," which misgeneralizes badly for sensor‑poor users (F1) — a small‑scale alignment failure: the system optimizes *producing a reading* over *being right*. Realign it toward **honesty** (say "I don't know") and **human feedback**.
- **Anti‑patterns:** optimizing for output completeness (always say something) over correctness; hiding the objective from the user; no interpretability.
- **Design implications:** make "I don't have enough to say" a first‑class, non‑failure output; align the system's implicit goal with the user's interest (honest reflection, not coverage).
- **Open research questions:** what is LOCA actually optimizing today, and does it match the user's interest? (Largely no.)
- **Ideas to experiment with:** reward the system (in design) for *appropriate silence*, not for filling every surface.

### 6. *Architects of Intelligence* — Martin Ford
Interviews with AI leaders reveal **wide disagreement and deep humility** about what AI can and can't do; timelines and capabilities are uncertain; hype outruns reality. The practitioners closest to the work are the most cautious.
- **Lessons for LOCA:** **epistemic humility** is the expert stance. LOCA should mirror it — claim less, hedge more, avoid the "confident oracle" persona that even AI leaders warn against. The overclaiming Life tab is the naive stance, not the sophisticated one.
- **Anti‑patterns:** oracle framing; implying the AI "understands" the user; hype language.
- **Design implications:** humble, hedged voice; never imply understanding beyond evidence; position LOCA as a mirror, not a mind.
- **Open research questions:** does a humble AI voice increase or decrease user trust and retention in a reflective product?
- **Ideas to experiment with:** A/B a confident vs humble voice for the same reading; measure trust.

### 7. *The Book of Why* — Judea Pearl
The **ladder of causation**: association (seeing) → intervention (doing) → counterfactual (imagining). **You cannot derive causation from correlation without a causal model**; observational data alone yields only association. Confounders masquerade as causes.
- **Lessons for LOCA:** LOCA's patterns are **rung 1 (association) only** — and must be presented as such. "On days you run, your mood is higher" is association; claiming running *causes* mood is a rung‑2 error LOCA must never make (R2/Haidt agrees). Confounders (a good week raises both) are rampant in life data.
- **Anti‑patterns:** any causal language ("X improved your Y"); implying intervention effects from observational correlation; ignoring confounders.
- **Design implications:** strictly associational, hedged language; surface possible confounders where honest ("both may reflect a good week"); reserve causal claims for user‑run n=1 experiments (the only rung‑2 evidence LOCA could earn).
- **Open research questions:** can LOCA support genuine n=1 interventions (rung 2) safely, or must it stay associational?
- **Ideas to experiment with:** an opt‑in "try changing X for two weeks" experiment that earns a weak causal signal honestly.

### 8. *Probabilistic Machine Learning* — Kevin Murphy *(reference)*
The Bayesian/probabilistic toolkit: **priors, likelihoods, posteriors**; principled **uncertainty** (aleatoric vs epistemic); graphical models; belief updating. The rigorous foundation for reasoning under uncertainty.
- **Lessons for LOCA:** LOCA's inference is *implicitly* Bayesian (priors like circadian baselines, evidence updating) but done ad‑hoc and **uncalibrated** (F1). A principled probabilistic frame would fix the renormalization bug and give honest **epistemic** uncertainty (wide when data is thin) for free.
- **Anti‑patterns:** ad‑hoc weight sums that don't normalize (F1); treating a thin‑data estimate as confident; conflating "no data" with "low value" (the exact F1 error — that's a prior‑vs‑posterior confusion).
- **Design implications:** re‑cast inference as prior + evidence → posterior with proper normalization and explicit epistemic uncertainty; low evidence → wide posterior → "not enough to say."
- **Open research questions:** would a principled Bayesian re‑implementation resolve F1/F2 cleanly and yield honest confidence?
- **Ideas to experiment with:** prototype one dimension (energy) as a proper Bayesian update and compare calibration to the current model.

## Part C — Research topics

### Group 1 — Explainability, uncertainty, epistemics *(LOCA's immediate D3/D4 core)*

**T1. Explainable AI (XAI).** Intrinsic interpretability vs post‑hoc attribution (LIME/SHAP); explanations must be **faithful** (reflect the real computation), not plausible‑sounding cover stories.
- *Lessons for LOCA:* LOCA can be **intrinsically interpretable** — it literally has `contributingSources`/`sampleCount`; surface them faithfully. → **D3**.
- *Anti‑patterns:* plausible but unfaithful explanations; hiding the real computation.
- *Design implications:* show the true contributors behind each reading; "why" = the actual factors.
- *Open questions:* what explanation depth do users want before it's noise?
- *Experiment:* a tap‑through "why this reading" showing real contributors + weights.

**T2. Human‑AI Interaction (HAI).** Amershi et al.'s guidelines; **appropriate reliance** (avoid over‑ and under‑trust); mixed‑initiative; make capabilities/limits clear.
- *Lessons for LOCA:* calibrate the user's trust to reality — don't induce over‑trust with confident prose over thin data (F1). → **D3**.
- *Anti‑patterns:* inducing over‑reliance; unclear limits.
- *Design implications:* signal confidence and limits inline; let the user correct.
- *Open questions:* what cues produce appropriate (not blind) reliance on LOCA?
- *Experiment:* confidence chips on every reading; measure calibrated trust.

**T3. Confidence estimation.** Model confidence ≠ correctness; neural softmax is famously overconfident; confidence must be earned from data density and agreement.
- *Lessons for LOCA:* derive confidence from **data density + source agreement** (LOCA has both), not from the model's raw output. → **D3/D4**.
- *Anti‑patterns:* presenting any reading at uniform confidence; overconfidence on thin data.
- *Design implications:* confidence as a function of n and agreement; suppress low‑confidence claims.
- *Open questions:* what confidence floor should gate a Life claim?
- *Experiment:* gate all Life prose on a confidence threshold.

**T4. Uncertainty estimation.** **Aleatoric** (irreducible noise) vs **epistemic** (reducible with more data); ensembles, Bayesian methods, **conformal prediction** for distribution‑free intervals.
- *Lessons for LOCA:* the sensor‑poor user's uncertainty is **epistemic** (fixable with data) — say so ("not enough yet"), don't render it as a low value (F1). → **D4**.
- *Anti‑patterns:* collapsing epistemic uncertainty into a point estimate; F1's "no data = low."
- *Design implications:* distinguish "unknown" from "low"; widen intervals when thin.
- *Open questions:* can conformal prediction give LOCA honest, simple intervals?
- *Experiment:* replace point states with ranges that visibly narrow as data grows.

**T5. Calibration of AI predictions.** Reliability diagrams, ECE, temperature scaling (Guo et al.); a calibrated "70%" is right ~70% of the time. Calibration is *the* trust metric for probabilistic claims.
- *Lessons for LOCA:* LOCA has no calibration story; micro‑check‑ins are a ready **ground‑truth** source to measure and correct it. → **D4**.
- *Anti‑patterns:* uncalibrated confidence numbers; never checking predictions against reality.
- *Design implications:* use check‑ins to calibrate; report calibrated confidence.
- *Open questions:* how quickly can per‑user calibration converge from check‑ins?
- *Experiment:* a reliability check comparing inferred states to explicit check‑ins.

**T6. Provenance & evidence attribution.** Data lineage; citations; every derived claim traces to sources. The foundation of trust (Apple Health, Perplexity).
- *Lessons for LOCA:* provenance‑by‑construction from the immutable log (Kleppmann) fixes F7/F8. → **D2/D3**.
- *Anti‑patterns:* claims without sources; seeded data unlabeled (F7).
- *Design implications:* origin tag + evidence pointer on every claim/entity.
- *Open questions:* what provenance granularity is useful vs cluttering?
- *Experiment:* an origin badge (user/inferred/calendar/seeded) on every Life entity.

### Group 2 — Reasoning: causal, Bayesian, temporal

**T7. Causal inference.** Pearl's ladder; confounders; no cause from correlation without a model.
- *Lessons for LOCA:* stay on rung 1; label everything associational. → **D3**.
- *Anti‑patterns:* causal claims from observational data.
- *Design implications:* associational language; surface confounders.
- *Open questions:* can LOCA ever earn rung‑2 evidence (n=1)?
- *Experiment:* opt‑in n=1 intervention.

**T8. Bayesian reasoning.** Prior + evidence → posterior; principled updating; thin evidence → wide posterior.
- *Lessons for LOCA:* re‑frame inference as Bayesian updating; fixes the prior/posterior confusion at the root of F1. → **D4**.
- *Anti‑patterns:* ad‑hoc weight sums; treating priors as measurements (the F1 error).
- *Design implications:* explicit prior/posterior separation; wide posterior when thin.
- *Open questions:* does a Bayesian rebuild resolve F1/F2 cleanly?
- *Experiment:* Bayesian energy‑model prototype.

**T9. Temporal reasoning.** Reasoning over time, order, duration, and sequence; essential for a life model.
- *Lessons for LOCA:* LOCA's chapters/events are temporal reasoning — strengthen ordering/duration honesty; it's a real strength if kept factual.
- *Anti‑patterns:* atemporal averages (R2/Kahneman); false sequencing.
- *Design implications:* reason in episodes/transitions, not means.
- *Open questions:* which temporal structures are most legible to users?
- *Experiment:* a timeline view emphasizing transitions.

**T10. Event detection.** Change‑point/anomaly detection in streams; separating signal from noise.
- *Lessons for LOCA:* `EventDetectionEngine` is this; ensure detected events are **evidenced** and not artifacts of F1‑deflated states. → **D4**.
- *Anti‑patterns:* "events" that are inference artifacts; unexplained events (D2).
- *Design implications:* events must cite the change they mark; user‑verifiable.
- *Open questions:* what's the false‑positive rate on real (non‑seeded) data?
- *Experiment:* validate detected events against user‑confirmed moments.

**T11. Time‑series reasoning.** Baselines, seasonality, trend, anomaly; the honest basis for "vs your baseline."
- *Lessons for LOCA:* build the **real baseline engine** (Oura, R1) — EMA/SD with disclosed n — replacing the placeholder (F6). → **D3/D4**.
- *Anti‑patterns:* fixed‑constant baselines (F6); ignoring seasonality.
- *Design implications:* adaptive personal baselines; disclose n.
- *Open questions:* how much history before a baseline is trustworthy for LOCA's signals?
- *Experiment:* per‑dimension rolling baseline with a "still learning" state.

### Group 3 — Memory, knowledge, retrieval *(mostly forward‑looking / V3+)*

**T12. Long‑term AI memory.** Memory beyond a context window; episodic vs semantic; retrieval‑based recall.
- *Lessons for LOCA:* LOCA's record *is* long‑term memory — treat it as an episodic/semantic store to **retrieve from**, not narrate over. Strength.
- *Anti‑patterns:* summarizing away the raw record; narration replacing retrieval.
- *Design implications:* retrieval‑first recall of the real record.
- *Open questions:* episodic vs semantic split for a life model?
- *Experiment:* "what happened around <date>" retrieval.

**T13. Memory architectures for LLMs.** Hierarchical/paged memory (MemGPT‑style), short/long‑term tiers, summarization for context.
- *Lessons for LOCA:* only relevant if an LLM enters; then tier raw record (authoritative) vs summaries (disposable). Keep raw immutable.
- *Anti‑patterns:* letting summaries become the source of truth (Schacter risk).
- *Design implications:* raw log authoritative; summaries as views.
- *Open questions:* does LOCA need this before an LLM? (No.)
- *Experiment:* defer until/unless generation is added.

**T14. Context engineering.** Assembling the right evidence for an inference/generation; retrieval + selection + ordering.
- *Lessons for LOCA:* for Ask and reflective prompts, assemble context **from the real record** (grounding) so outputs can't drift from fact.
- *Anti‑patterns:* generating without grounding context.
- *Design implications:* every generated surface grounded in retrieved real events.
- *Open questions:* what context yields the best reflective prompt?
- *Experiment:* prompt‑from‑retrieved‑moment pipeline.

**T15. Knowledge representation.** Symbolic (ontologies, triples) vs sub‑symbolic; how to store "who/what/when."
- *Lessons for LOCA:* LOCA's People/Events/Chapters are an implicit **symbolic graph** — make nodes/edges explicit with provenance + confidence.
- *Anti‑patterns:* opaque entities without type/provenance (F7).
- *Design implications:* typed nodes/edges, each with origin + confidence.
- *Open questions:* how rich a schema before it's over‑engineered?
- *Experiment:* a typed entity schema with mandatory provenance.

**T16. Personal knowledge graphs.** Entity‑relationship graph of a person's life; nodes with source + confidence + time.
- *Lessons for LOCA:* this is LOCA's right long‑term substrate (People↔Events↔Chapters↔Habits) — but only if every node exposes origin + confidence. → **D2**.
- *Anti‑patterns:* mystery nodes (Sarah/Alex, F7); edges without evidence.
- *Design implications:* PKG with provenance‑bearing nodes/edges; user‑editable.
- *Open questions:* what relations are honest to infer vs must be user‑confirmed?
- *Experiment:* render People as a provenance‑labeled graph the user can correct.

**T17. Retrieval‑Augmented Generation (RAG).** Retrieve grounding, then generate; reduces hallucination; enables citations.
- *Lessons for LOCA:* if generation is ever added (Ask), **RAG over the real record** with citations is the only safe form. Grounding = the record.
- *Anti‑patterns:* ungrounded generation about the user's life.
- *Design implications:* retrieve real events → generate → cite them.
- *Open questions:* is Ask better as RAG or as deterministic composition (current)?
- *Experiment:* RAG‑Ask prototype with mandatory citations, compared to current.

**T18. Semantic search.** Embedding‑based retrieval by meaning, not keywords.
- *Lessons for LOCA:* could power "search your life" over notes/logs (Rewind‑style) — an honest, zero‑claim retrieval feature.
- *Anti‑patterns:* semantic search that fabricates or ranks opaquely.
- *Design implications:* on‑device embeddings over the user's own record.
- *Open questions:* is semantic search worth the complexity vs structured queries?
- *Experiment:* semantic search over logged notes.

**T19. Vector databases.** ANN indices storing embeddings for fast similarity retrieval.
- *Lessons for LOCA:* only if semantic search/RAG is adopted; must be **on‑device** (privacy). Otherwise unnecessary complexity.
- *Anti‑patterns:* adding a vector DB for sophistication with no user need; cloud storage of personal embeddings.
- *Design implications:* on‑device ANN only, or skip.
- *Open questions:* does LOCA's data volume justify ANN vs brute‑force on device?
- *Experiment:* benchmark on‑device brute‑force vs ANN at realistic scale.

**T20. Hybrid retrieval.** Dense (embeddings) + sparse (BM25) + reranking; robust retrieval.
- *Lessons for LOCA:* relevant only if retrieval is central; structured filters over the record may beat both for a small personal corpus.
- *Anti‑patterns:* over‑engineering retrieval for a tiny personal dataset.
- *Design implications:* prefer structured + simple retrieval at personal scale.
- *Open questions:* what retrieval wins at one‑person data scale?
- *Experiment:* compare structured vs hybrid on the personal corpus.

**T21. Memory compression & summarization.** Hierarchical/salience‑based summarization to fit context and aid recall.
- *Lessons for LOCA:* summaries are **views**, never the source; salience = peaks/transitions (Kahneman/Heath, R2). Keep raw immutable.
- *Anti‑patterns:* lossy summaries overwriting the record; averaging away peaks.
- *Design implications:* peak/transition‑preserving summaries as disposable views.
- *Open questions:* what salience model best matches human memory?
- *Experiment:* a peak‑preserving month summary vs an averaged one.

### Group 4 — Learning loops & agents

**T22. Human feedback loops.** RLHF/active learning; the human teaches the system; corrections are gold.
- *Lessons for LOCA:* surface `FeedbackProcessor`/`SensorConflict` — make the user the teacher (R1/RescueTime). → **D4**.
- *Anti‑patterns:* no visible correction path; ignoring conflicts.
- *Design implications:* one‑tap "that's wrong" everywhere, feeding updates.
- *Open questions:* how much does a little feedback improve LOCA's accuracy?

**T23. Learning from corrections.** Incorporating user corrections to update models/beliefs.

- *Open questions:* per‑user vs population correction learning?
- *Experiment:* show a reading changing after a correction.

**T24. Continual learning.** Learning over time without **catastrophic forgetting**; adapting as the person changes.
- *Lessons for LOCA:* a life model must adapt as the user changes (new chapter, new baseline) without forgetting history — the honest record preserves the past; baselines adapt.
- *Anti‑patterns:* baselines that forget; or models that never adapt.
- *Design implications:* adaptive baselines + immutable history (best of both).
- *Open questions:* how fast should baselines adapt across a life transition?

**T25. Online learning.** Incremental per‑sample updates from streaming data.

- *Anti‑patterns:* unstable per‑sample swings; non‑idempotent updates.

**T26. Agent architectures.** ReAct, planning, tool‑use, self‑reflection loops.

- *Anti‑patterns:* agentifying a deterministic pipeline for sophistication.
- *Design implications:* keep it a pipeline unless a clear user need for tool‑use emerges.
- *Open questions:* is there any honest agentic use case in LOCA?
- *Experiment:* defer.

**T27. Multi‑agent systems.** Specialized agents + orchestration.
- *Lessons for LOCA:* **not applicable**; would add opacity and coordination cost with no user benefit at personal scale.
- *Anti‑patterns:* multi‑agent complexity as theater.
- *Design implications:* avoid.
- *Open questions:* none pressing.
- *Experiment:* none.

### Group 5 — Systems that model people; privacy

**T28. Personal AI systems.** Assistants that model an individual over time; personalization vs privacy tension.
- *Lessons for LOCA:* LOCA is one of these; its edge is **local‑first privacy** + honest modeling. Personalize from the user's own data only.
- *Anti‑patterns:* population models masquerading as personal (the F6 placeholder is a population prior mislabeled "yours").
- *Design implications:* strictly personal baselines/models; disclose any population prior.
- *Open questions:* how to bootstrap before personal data exists without lying?
- *Experiment:* explicit "using typical ranges until we learn yours" state.

**T29. AI assistants that model people over time.** User modeling, preference learning, long‑horizon personalization; risk of stale or wrong models.
- *Lessons for LOCA:* keep the user model **correctable and current**; a wrong, sticky model of a person is uniquely alienating (F7's mystery people).
- *Anti‑patterns:* stale/uncorrectable user models; asserting preferences.
- *Design implications:* user‑visible, user‑editable model; decay stale beliefs.
- *Open questions:* how to age out beliefs the data no longer supports?
- *Experiment:* a "what LOCA thinks it knows about you" editable panel.

**T30. Digital twins / personal digital memory systems.** A dynamic model of a real entity updated by its data (industrial twins); lifelogging (MyLifeBits, Rewind).
- *Lessons for LOCA:* LOCA is a **personal digital twin** — but a twin is only as good as its fidelity; a *low‑fidelity twin that speaks confidently* (F1) is worse than none. Fidelity and honesty first.
- *Anti‑patterns:* a confident low‑fidelity twin; lifelog surveillance dread.
- *Design implications:* match confidence to fidelity; privacy‑first capture.
- *Open questions:* what fidelity threshold justifies twin‑level claims?
- *Experiment:* fidelity‑gated claims (only speak where the twin is well‑fed).

**T31. Personal data privacy & on‑device AI.** Local‑first, on‑device inference, differential privacy, federated learning; keeping personal data on the device.
- *Lessons for LOCA:* LOCA's **local‑first, on‑device** stance is a genuine strategic asset and trust foundation (and dodges the graveyard's exploited‑data mode, R3). Protect and foreground it.
- *Anti‑patterns:* moving personal data or embeddings off‑device; cloud dependence for core features.
- *Design implications:* keep inference/retrieval on‑device; foreground privacy as a promise; any future LLM should be on‑device or privacy‑preserving.
- *Open questions:* can any needed generation run on‑device to preserve the promise?
- *Experiment:* evaluate on‑device small models for reflective prompting.

## Part D — R4 synthesis

### What actually works for personal intelligence (the durable findings)
1. **Ground over generate** — tie every claim to retrieved evidence (Kleppmann's log → views; RAG). LOCA has the log; it must carry provenance forward.
2. **Calibrated, honest uncertainty** — distinguish "unknown" (epistemic) from "low," widen when thin, calibrate against ground truth. Fixes F1 at the root.
3. **Provenance by construction** — from an immutable event log, lineage is a query, not an add‑on. Fixes F7/F8.
4. **Human‑in‑the‑loop correction** — the user teaches; corrections visibly update. Activates LOCA's dormant `FeedbackProcessor`.
5. **Stay on the causal ladder's rung 1** — association only, unless the user runs an n=1 intervention. Kills causal overreach.
6. **Episodic memory + retrieval beats narration** — LOCA's record is its best AI asset; retrieve from it, don't narrate over it.
7. **On‑device/local‑first is a moat** — privacy is trust; keep it.

### Anti‑patterns (AI‑specific, additive to R2/R3)
- Confident output over thin data (F1) — the cardinal epistemic sin.
- Discarding computed provenance/uncertainty (F8).
- Treating "no data" as "low value" (prior/posterior confusion, F1).
- Causal claims from correlation (rung‑2 error).
- Population priors mislabeled as personal (F6).
